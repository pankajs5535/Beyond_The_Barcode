-------------------------------------------------------------------------------
1. UNDERSTANDING UNIT TESTING
-------------------------------------------------------------------------------

WHAT IS UNIT TESTING?

    Unit testing means testing a small, individual part of an application
    independently from external dependencies.

    In this project, SupplierService is the unit being tested.

REAL-WORLD EXAMPLE:

    Suppose an ERP system has 1,000 suppliers.

    When a user searches for supplier ID 1, the application should return
    the correct supplier details.

    A unit test verifies this behavior automatically without requiring
    a real database.

WHY IS IT USED IN ENTERPRISE PROJECTS?

    - Detects defects early.
    - Verifies business logic.
    - Prevents existing functionality from breaking.
    - Makes refactoring safer.
    - Reduces repetitive manual testing.
    - Helps developers maintain reliable applications.

IMPORTANT:

    Unit testing does not prove that the entire application works.
    It verifies the specific behavior covered by the tests.

-------------------------------------------------------------------------------
2. UNDERSTANDING THE DEPENDENCIES
-------------------------------------------------------------------------------

SupplierService depends on IUnitOfWork.

IUnitOfWork provides access to ISupplierRepository through its Suppliers
property.

The repository performs operations such as:

    - Retrieving suppliers.
    - Adding suppliers.
    - Updating suppliers.
    - Deleting suppliers.
    - Searching suppliers.
    - Checking whether supplier codes and tax numbers exist.

NORMAL APPLICATION FLOW:

    API Controller
          |
          v
    SupplierService
          |
          v
    IUnitOfWork
          |
          v
    ISupplierRepository
          |
          v
    Database

UNIT TEST FLOW:

    SupplierServiceTests
          |
          v
    Actual SupplierService
          |
          v
    Mock IUnitOfWork
          |
          v
    Mock ISupplierRepository
          |
          v
    Predefined Test Data

IMPORTANT:

    SupplierService is REAL.

    IUnitOfWork is MOCKED.

    ISupplierRepository is MOCKED.

    No real database is required for these unit tests.

The mocked repository returns the test data configured by the developer.

3. UNDERSTANDING THE TEST CLASS FIELDS
-------------------------------------------------------------------------------

FIELD 1:
    private readonly Mock<IUnitOfWork> _unitOfWorkMock;

PURPOSE:

    Creates a mock implementation of IUnitOfWork.

WHY IS IT REQUIRED?

    SupplierService depends on IUnitOfWork.

    Instead of creating the real UnitOfWork, we create a mock that allows
    us to control the behavior of its dependencies.

REAL-WORLD EXAMPLE:

    Instead of connecting to SQL Server, the test provides a fake repository
    that returns predefined supplier information.

-------------------------------------------------------------------------------

FIELD 2:
    private readonly Mock<ISupplierRepository> _supplierRepositoryMock;

PURPOSE:

    Creates a mock implementation of ISupplierRepository.

WHY IS IT REQUIRED?

    It allows us to control what happens when SupplierService calls
    repository methods.

EXAMPLE:

    When GetByIdAsync(1) is called, the mock can return a Supplier object.

    When GetByIdAsync(99) is called, the mock can return null.

    This allows us to test both situations without a database.

-------------------------------------------------------------------------------

FIELD 3:
    private readonly SupplierService _supplierService;

PURPOSE:

    Stores the actual SupplierService object being tested.

IMPORTANT:

    We do not mock SupplierService itself.

    We create the actual service and provide its dependencies through
    dependency injection.

WHY?

    We want to test the real implementation of SupplierService rather
    than testing the behavior of another mock.

-------------------------------------------------------------------------------
4. TEST CLASS CONSTRUCTOR
-------------------------------------------------------------------------------

CONSTRUCTOR:
    public SupplierServiceTests()

PURPOSE:

    Initializes the mock objects and creates the actual SupplierService.

STEP 1:
    _unitOfWorkMock = new Mock<IUnitOfWork>();

EXPLANATION:

    Creates a mock of IUnitOfWork.

    The mock allows us to configure how the UnitOfWork behaves during tests.

STEP 2:
    _supplierRepositoryMock = new Mock<ISupplierRepository>();

EXPLANATION:

    Creates a mock of ISupplierRepository.

    Repository methods can now return predefined results.

STEP 3:
    _unitOfWorkMock
        .Setup(u => u.Suppliers)
        .Returns(_supplierRepositoryMock.Object);

EXPLANATION:

    Setup() configures the behavior of a mock.

    u => u.Suppliers identifies the Suppliers property.

    Returns() specifies what the mock should return when that property
    is accessed.

    _supplierRepositoryMock.Object provides the actual mock object that
    SupplierService can use through the ISupplierRepository interface.

RESULT:

    Whenever SupplierService accesses _unitOfWork.Suppliers, it receives
    the mocked SupplierRepository.

STEP 4:
    _supplierService =
        new SupplierService(_unitOfWorkMock.Object);

EXPLANATION:

    Creates the real SupplierService.

    _unitOfWorkMock.Object provides the mock implementation of IUnitOfWork.

    The service receives that mock through its constructor.

WHY IS THIS IMPORTANT?

    Dependency injection allows us to replace real dependencies with
    mocks during unit testing.

CONSTRUCTOR EXECUTION:

    xUnit creates a new instance of the test class for each test.

    Therefore, the constructor prepares fresh mocks for each test.

6. ARRANGE, ACT, ASSERT (AAA) PATTERN
===============================================================================

Most unit tests follow three steps.

ARRANGE:

    Prepare test data and configure mock behavior.

    Example:
        Create a Supplier object.
        Configure GetByIdAsync(1) to return that supplier.

ACT:

    Call the actual service method being tested.

    Example:
        await _supplierService.GetByIdAsync(1);

ASSERT:

    Verify that the result matches the expected behavior.

    Example:
        Assert.NotNull(result);
        Assert.Equal("SUP001", result.SupplierCode);

WHY IS AAA IMPORTANT?

    It separates preparation, execution, and verification.

    This makes unit tests easier to understand, debug, and maintain.

25. WHY MOCKING IS IMPORTANT
===============================================================================

WITHOUT MOCKING:

    Tests may depend on:

        - A running database.
        - Existing database records.
        - Database configuration.
        - External infrastructure.

    These dependencies can make tests slower and harder to control.

WITH MOCKING:

    Tests can provide predefined responses without using a real database.

BENEFITS:

    1. Faster execution.
    2. Predictable test data.
    3. Independent testing of service logic.
    4. Easier testing of success and failure scenarios.
    5. No need to insert test records into SQL Server.
    6. Easier diagnosis when a test fails.

IMPORTANT LIMITATION:

    Mocking the repository does not test the repository's actual database
    queries.

    Repository queries, Entity Framework Core configuration, and database
    integration should be covered by appropriate integration tests.

26. WHY ASYNC AND AWAIT ARE USED
===============================================================================

Many service and repository methods return Task or Task<T>.

For example:

    Task<Supplier?> GetByIdAsync(int id);

This indicates that the operation is asynchronous.

In a test, we use:

    var result = await _supplierService.GetByIdAsync(1);

WHY?

    await waits asynchronously for the operation to finish and provides
    its result.

    It allows the test to assert the returned value after the service
    method has completed.

IMPORTANT:

    Do not block asynchronous test execution unnecessarily using .Result
    or .Wait().

29. UNIT TESTING VS INTEGRATION TESTING
===============================================================================

UNIT TESTING:

    Tests SupplierService using mocked dependencies.

    Database required:
        No.

    Main objective:
        Verify service behavior independently.

INTEGRATION TESTING:

    Tests how multiple components work together, such as the service,
    repository, Entity Framework Core, and a test database.

    Database required:
        Usually a test database or suitable database test environment.

    Main objective:
        Verify that the components work together correctly.

EXAMPLE:

    Unit test:
        Verify that GetByIdAsync returns the DTO when the mocked repository
        returns a Supplier.

    Integration test:
        Insert a Supplier into a test database and verify that the actual
        repository retrieves it correctly.

BOTH TYPES ARE USEFUL:

    Unit tests help isolate defects in individual components.

    Integration tests help identify problems between connected components.
